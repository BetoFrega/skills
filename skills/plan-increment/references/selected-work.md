# Selected work

Read this when developing vertical cuts, checking an existing increment, or scoping
discovery. [Canonical slice meanings](../../consolidate/references/delivery-slices.md)
own identity, representation, acceptance, exposure, and observation requirements.
This reference owns how to develop the selected scope into workable cuts.

## Bound the selection

Use the next result or set of increments selected by the user. Develop a broad idea
with [product grilling](../../grilling/references/product-increments.md) until a
consistent candidate can be formulated. Apply the same sufficiency check to an
existing record without repeating settled questions. Keep later capabilities and
nonessential cases deferred; include cross-cutting work only when it gates this result.

Identify the actor's usable end-to-end outcome. Narrow audiences, conditions, cases,
or capability while preserving that outcome and its necessary layers. A database,
endpoint, or interface fragment alone is enabling work, not a usable product slice.
A complete result may depend on an earlier increment with an explicit satisfaction
condition. Delivery need not be useful to every eventual audience at once.

Each increment has its own verifiable acceptance, relevant exceptions, prerequisites,
and exposure strategy. Generally propose a dedicated flag for independent exposure;
retain existing controls when appropriate and explain shared controls or alternatives.
Define disabled behavior and material exposure prerequisites. Keep proposed control
names separate from observed provider identifiers and flag state. A slicing decision
does not authorize operating a flag, releasing, or claiming availability.

## Resolve consequential uncertainty

Read product rules, evidence, relevant technical constraints, and prior decisions.
Use grilling for choices that would change outcome, scope, acceptance, or prerequisites.
Leave routine implementation choices to execution. A technical spec is useful when
the selected work needs one; it is not a mandatory phase for every increment.

When evidence indispensable to a coherent cut is missing, use the product interview's
bounded discovery handoff. Define the question, method, scope, expected evidence or
output, and completion criterion. An investigation, prototype, or experiment can be
executable work without an approved feature commitment. Keep its learning result
distinct from a product delivery claim. Prefer a smaller usable cut when it still
advances the user's goal rather than waiting on unrelated uncertainty.

## Preserve aggregate meaning

Persist accepted definitions through [consolidate](../../consolidate/SKILL.md), using
its slice template and configured representation. Reference the parent functionality's
rules and scenarios; record only scope-specific differences. Stable references link
the increment to its execution work, evidence, and prerequisite increments.

Account for selected scenarios as covered, deferred, or unresolved, with reasons.
Do not invent future cuts to exhaust the feature's full scenario inventory. Broader
canonical knowledge remains available without becoming part of this workset.

An increment's coherent outcome determines its scope. Execution tickets can be smaller
for reliable implementation and verification; preserve their shared increment reference
and aggregate acceptance. Shared enabling work can serve several selected increments
without pretending to be independently useful product delivery.
