# Triage

Resolve tracker workflow, role-label mapping, and external-PR scope through [project configuration](../setup-beto-frega-skills/references/project-configuration.md), including project-scoped external files. If mapping is missing, direct the user to invoke `/setup-beto-frega-skills`.

Treat configured external PRs as issues with attached code; resolve bare numbers through tracker configuration. Every posted tracker comment or issue starts with:

```markdown
> *This was generated by AI during triage.*
```

Report local tracker/`.out-of-scope/` edits using [local document delivery](../consolidate/references/local-document-delivery.md).

## Roles and transitions

Assign exactly one category and state:

- Categories: `bug` (broken behavior), `enhancement` (feature/improvement).
- States: `needs-triage` (maintainer evaluation), `needs-info` (reporter input), `ready-for-agent` (fully specified AFK work), `ready-for-human` (human implementation), `wontfix` (no action).

For PRs, `ready-for-agent` means a brief and agent action on the diff; `ready-for-human` means ready for human merge.

Normally: unlabeled → `needs-triage` → another state; reporter replies return `needs-info` to `needs-triage`. Maintainers may override. Conflicting states require maintainer clarification before anything else; flag unusual transitions and ask before proceeding.

## Attention queue

Interpret the maintainer's natural-language request. For discovery, show three buckets oldest first: unlabeled, `needs-triage`, and `needs-info` with reporter activity since last triage notes. Include counts and one-line summaries; let the maintainer choose.

Include only configured external PRs in discovery, tagging entries `[PR]`/`[issue]`. Explicitly named PRs are triaged regardless of author.

## Triage an item

1. Read body, comments, labels, author, dates, and PR diff. Parse prior triage notes and reporter replies; present updates without re-asking resolved questions. Explore code using the domain glossary and applicable ADRs. Search for existing behavior by domain concept and report search locations; existing implementation leads to `wontfix`. Read `.out-of-scope/*.md` for similar prior rejections.
2. Recommend category/state with reasons and relevant codebase summary, including existing implementation. Wait for direction.
3. Before grilling, verify claims: reproduce bugs from reporter steps; check out PRs and run relevant tests/commands. Report confirmed with code path, failed, or insufficient detail (`needs-info`).
4. If clarification is needed, invoke [grilling](../grilling/SKILL.md) and [domain-modeling](../domain-modeling/SKILL.md). Ask one round at a time; sharpen domain terms and update `CONTEXT.md`/ADRs as decisions land.
5. Apply the outcome:
   - `ready-for-agent`: post [agent brief](AGENT-BRIEF.md).
   - `ready-for-human`: same brief structure; explain why delegation is unsuitable.
   - `needs-info`: post `Triage Notes` with established facts and specific actionable questions mentioning the reporter. Preserve resolved grilling decisions.
   - `wontfix`: close with reason. Already implemented: link implementation; leave the rejection KB untouched. Rejected bug: polite explanation. Rejected enhancement: write [out-of-scope record](OUT-OF-SCOPE.md), link it in the comment, then close.
   - `needs-triage`: apply role; partial-progress comment optional.

## Direct override

Trust explicit state overrides. Confirm intended role changes/comments/closure, then act; skip grilling. For `ready-for-agent` without grilling, ask whether the maintainer wants an agent brief.
